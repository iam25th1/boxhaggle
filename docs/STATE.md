## Known risks

- `/mcp` lets anyone open sessions (rate limited per client IP, 5,000 sessions at most, 60 minute TTL). Same exposure as the plugin path, where PayBox adds the key for any user.
- A plugin-channel session binds to its first payer, so whoever learns a session id before the first payment could pay first and lock the owner out. Session ids are 128-bit random, are never listed, and only travel in the owner's chat and tool results.

- In-memory state on one instance; a restart drops open sessions. Keep one replica.
- 8 moderate advisories, all transitive through `@paybox-sh/sdk@2.2.0` > `@solana/web3.js@1.98.4` > `jayson@4.3.0` (`uuid@8.3.2` v3/v5/v6 buffer bounds, `stream-json@1.9.1` DoS and prototype pollution). Agent only; the merchant image does not include the SDK. No upstream fix without a breaking SDK change. The high-severity `ws` advisory is fixed by an override to `ws@8.22.0`.
- GitHub Actions are pinned by major tag, not commit SHA.
- `TRUST_PROXY=1` trusts `X-Forwarded-For`; set it only behind Railway's proxy (alternate deploy).
- `TRUST_CF_CONNECTING_IP=1` trusts the header from any loopback peer, so a process on the host can pick its own rate-limit key. The host is inside the trust boundary.
- Uptime depends on one host: it never sleeps and boots after a power cut, but a reboot that waits for an operator keeps both services down until someone acts.
- The PayAI facilitator is a third party; swapping facilitators is one env var.
- Solana exact payments carry a blockhash that lives 150 slots (about 32 seconds at 214 ms per slot, measured 2026-10-17). On `/mcp` the model relays PayBox's signed payment, and the two real runs took 42 and 46 seconds from signing to arrival, so a slow agent's payment expires on the way. It is refused as `payment_expired`, nothing is charged, and the agent is told to pay again and retry at once. The plugin path does not relay through the model: PayBox retries the endpoint itself. The MCP App now pays through PayBox `use_service`, which does the same; `pay_x402` is the fallback.
- `/mcp-pay` is keyless by design: anyone holding an MCP session id can pay a round on it, and the first payer binds the session (same exposure as plugin sessions). The id travels in the `use_service` url, so it also sits in the user's PayBox request history. Session ids are 128-bit random and the merchant's request log (operator only) records paths with the full id, as it already does for `/session/:id`.
